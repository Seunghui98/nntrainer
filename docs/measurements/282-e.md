## 3. p4096

- The prefill's `nntr_hvx_mm_u8i4_layer_res_add failed: err=39` is **not** where it
  starts. Logcat shows the first error, 36 s earlier in the same prefill:
  ```
  W nntrainer: HTP quantized KV cache: register failed: 0x8000040d
  E … Error 0x27: remote_handle64_invoke failed … method 31 …
  ```
  The lazy quantized-cache register (`kv_cache_q_register`, `max_rows` 4 160) faults the
  DSP PD (0x8000040d). Every later call, `res_add` included, then reads 0x27
  (`AEE_ENOSUCH`, no such session), and the close reads `info rc 0x27`.
- It is the same at C 16, 24 and 8 (`s1_arena_mib` 384 at C 8). So it is not the arena.
  It is the heap-growth path running out of 32-bit address space: 30 caches of about
  31 MiB (sliding) and 17 MiB (full) at 4 160 rows, ≈ 894 MiB, beside the prefill
  workspace. This is the same fault class as the FastRPC stack crash (aea5762c3: a
  malloc's heap growth faulting in `apps_mem_request_map64`).
- **The rows are already prompt + G** (4 160 = 4 096 + 64, init_seq_len = max_seq_len), so
  "shrink to prompt + G" buys nothing. What would: the sliding layers' quantized cache
  sized to their window (1 024 rows + the prefill chunk: −75 % of 850 MiB), or int4
  quantized prefill caches. Both are prefill-kernel changes; neither is done here.
- No reboot (uptime 9010 → 9309 is the cell's own time).

  the prefill, which the decode attention does not run, so it would not gate the int8
