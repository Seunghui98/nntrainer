## Why

This is the first time the 26B file runs on the phone. LEDGER ㊶ asks three
things. Does the one-PD E2E path (`NNTR_HTP_E2E=1`) load and run Gemma-4
26B with QS2CX_WH experts through the pool? Are its tokens the hybrid
path's tokens on the same file? What are tok/s, memory and the miss
cost for each pool size C? These are the ㉟ baseline that S6's levers
start from.

**The weights are a DUMMY.** The text is meaningless and is never
reported here. Every miss number comes from the dummy's routing (the
generated stream alternates between two token ids). The misses/token
column therefore does not predict the real checkpoint.

Cause, from the code (the frames above are symbolized against
`jni/obj/local`). `build_rope_table` calls
`precompute_freqs(head_dim, max_position_embeddings, …)`. Gemma-4 has
`max_position_embeddings` = **262 144**, so the fp32 tables it builds
are 262 144 × head_dim × 2 × 4 B: 512 MiB at head_dim 256 plus 1 GiB at
512. That is 1.5 GiB of `vector<vector<float>>`, on top of the fp16
tables the CPU prefill had already built (768 MiB; Android builds have
`ENABLE_FP16`). The DSP only uses `max_timestep` rows (≤ 2048). The
max_seq_len lever in the brief does not apply, because the table is
sized by `max_position_embeddings`, not `max_seq_len`.

**The lever I used was config only, no code:** `text_config.max_position_embeddings`
262144 → 4096, set in the device copy of `config.json`. This leaves the
numbers unchanged for positions < 4096. Sliding layers use RoPE `default`
and full layers use `proportional`, and neither theta depends on
`max_position_embeddings` (`_compute_proportional_parameters(head_dim, theta)`).
Every run below uses it, A and E alike. The real fix is to size the
table by `max_timestep` at `mha_core.cpp:681` / `:1551` / `:1602`. That
is left as a follow-up, not done in this sitting.

**Superseded by #253** (`docs/plans/253-rope-table-size.md`, LEDGER
rule 71): the table is now `max_timestep` rows, so the device's original
`config.json` loads as is and the 4096 edit is no longer needed.

**Reading.** Taken literally, "E == off over the run's count" does not
hold (57 / 65). What does hold:

* The prefill MoE is bit-identical.
* The first 16 tokens are identical (8 / 8 is the host gate's count).

E and off cannot be bit-identical over decode anyway. E runs FC,
attention, norm and LM head on the DSP, and off runs them on the CPU
(LEDGER rule 39). I judged that this is not the gate failure the brief
meant, and I ran the speed cells. **If you read the gate literally, the

There is no layer to name: decode MoE inside the token is not dumpable
from ARM. Prefill MoE is identical through call 30, and the logits

context: 9.8 → 13.9 → 17.8 ms.

## What did not run, and why

* **The CPU-only run (`moe_engine` cpu).** ㊶ names it as A, but the
  brief chose the hybrid `off` as the reference, and I followed the
  brief. The dummy's FC Q4_0 is ARM-interleaved, so a host x86 run
  cannot read it (PR #251).
* **Prompt 512.** The config's `sample_input` is 447 tokens with this
  tokenizer. I did not substitute another prompt.
* **Second runs.** G 512 / 1024 have one run per cell except the
  headline E16 G 512. The E spreads are small (≤ 1 % at G 64 r1 vs r2
  apart from E40). A16 G 64 spread is large (16.97 / 20.83, across the
  reboot).
* **Text / PPL columns.** None: the weights are a dummy.
* **No kernel or code patch.** The only deviation is the config copy's
  `max_position_embeddings`.
