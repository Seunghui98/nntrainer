## Why
Step 1 (`260-step1-4415-pure.md`, @ 86bb496b6) carried #4415's DSP router bug:
`hvx_router_rows_f32` accumulated in qf32, giving NaN rows on V79, NaN MoE
output and garbage text (their doc 57 §9.20–9.21). `7eeea62e7` fixes it
(IEEE sf accumulation). The delivered file is quantized from the real fp32
checkpoint, so the text and the prompt nll are now gates beside the speed
columns.

### Verdict
- **Text gate, first 64 tokens: pass on all three configurations.** Each is a
  faithful, on-topic summary of its prompt (the Thyme abstract; the Ardley
  harbour passage).
  - q8 shows one stray token "(Soruce_1)" at 447; fp16 does not.
  - The q8 p1022 text opens with a literal `<text>`.
- **Long generation (G512): fail on q8, both prompts.** The text falls into
  a greedy repetition loop after roughly 120–250 words. This was not run on
  fp16 or on the CPU in this sitting, so it is not attributed: it may be the
  model under greedy decoding or the NPU decode path. Their doc 57 §10.15
  reports a similar loop on a CPU QS4CX decode path.
- **Prompt nll: pass.** 447 q8 reads 4.429 and fp16 reads 4.439, both at or
  below their CPU reference 4.458.
- **Speed:**
  - Prefill reads about **128–140 tok/s at 447** and **≈ 212 tok/s at 1022**,
    with the router fixed. The 447 G64 cell (3492 ms) is 9 % slower than the
    447 G512 cell (3196 ms) on the same config; one run each.
  - Decode reads **2.6–3.5 tok/s**, lower than step 1's 3.8–6.9. The step 1
    decode was inflated by the bug, very probably: NaN routing picked
    experts 0..7 every token, so the per-layer LRU always hit. Real routing
    misses more.
  - fp16 KV against q8 at 447 G64: prefill +4 % (133.6 vs 128.0), decode
    +16 % (3.50 vs 3.02), nll +0.010.
- Step 1's numbers (@ 86bb496b6) are superseded: that prefill was
  numerically broken.
