## 1. Revision 3 as merged did not run (the crash and its fix)

Every cell on `19dbf3a78` (E and A, p512 / 1024 / 2048, E at C 16 / 12 / 8) died 6.8 s into the load:

```
[!] FATAL ERROR: Failed to repack weights: nntr_hvx_mm_u8i4_moe_layer failed: err=-2147482611
```

The DSP crash report has `__wrap_malloc` → `err_Fatal_internal0` → a fault at `apps_mem_request_map64+0x0`, Bad VA 0x70. The caller is `hexkl_moe_scratch_reserve+0x28` ← `hexkl_mm_u8i4_moe_layer_run+0x7D8`, running the load-time MoE warm-up on the FastRPC thread.

| probe (one cell each) | app | skel | result |
|---|---|---|---|
| r3 as merged, A / E p512 G64 | r3 | r3 `ed3658c0…` | crash |
| control: pure #4415 @ 2db6cad59, A q8 p1024 G64 (`s4415r3/`) | pure | pure `09e95513…` | **ran: 3,716 ms / 275.6 tok/s prefill**, decode 2.89, Ardley summary |
| r3 with the inline HMX path off | r3 | `e342d7c9…` | crash |
| cross | pure | r3 `ed3658c0…` | crash: the skel triggers it |

Cause: `hexkl_mm_u8i4_moe_layer_run`'s stack frame is 0x3a80 = 14,976 B on revision 3. It was 12,928 B on the pre-merge builds that ran, and 5,496 B on pure 2db6cad59. The FastRPC thread runs at the 16 KiB default, and the malloc's heap-growth path overflowed it. Fix: `093008229` (in `htp_decode` as `aea5762c3`, PR #278) sets the thread stack to 64 KiB, the same as the dspqueue thread. The tables below are on that fix.

Pure upstream on this unit reads 275.6 tok/s at p1024 (q8 KV), against 233.6 for 41bd65e04 in the r2 sitting. The revision-3 prefill gain is real.
