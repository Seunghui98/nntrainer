# 141 — dspqueue vs FastRPC round-trip microbench (step 1 only)

Issue: dlwlzzero/nntrainer#141 (p1, part of #76). Read against `htp_moe` @
`bb845426` (cycle 20, 2026-09-28; #132 PR 1 merged, so the ladder is
95 → 73 → **51** → 3 → 1). **Scope: the issue's step 1 only.** This is a
device microbench whose result decides between step 2 (adopting dspqueue
for the per-token entry) and releasing #132 PR 2. The plan changes no model
path. The bench adds two DSP test methods, one gtest binary and a guard
line in `build.sh`. It is sized for about one hour of implementation.

## 1. Goal and gate

**Goal.** Measure on the device, in one binary and one session:

* (a) the per-round-trip cost of the existing minimal FastRPC invoke;
* (b) a dspqueue request/response round trip with a 12 KiB payload, through
  an rpcmem buffer the DSP already maps, answered by a DSP thread parked on
  the queue.

Both run at the sitting's QoS (`qos_mode=2`, `NNTR_HTP_POLL_US` unset =
5000 µs, `htp_backend.cpp:76-104`). Each is reported as median, p90, min
and max over 1000 timed round trips after 100 warm-up round trips.

**Gate (measurable).** `unittest_hvx_dspq` prints the lines below and
ends in `[  PASSED  ]`:

* `DSPQ_BENCH env ...`
* the three `DSPQ_BENCH row=F*` lines
* the eight `DSPQ_BENCH row=Q*` lines, each with `bad=0`
* `DSPQ_BENCH dsp_stats ... bad=0`
* `DSPQ_BENCH verdict ...`

`bad=0` means every response carried the right sequence number and the
right echoed payload (first, middle and last word). Each of those rows is a
bit-identity check of the 12 KiB copy through the queue and its cache
maintenance.

The result goes into a BENCHMARK.md side table of the sitting it rides. It
is never a tok/s cell.

**Standing gates** (prefill ≥ −5 % of A, text identical to the CPU run /
the per-token-entry text rule). No model path changes here. The IDL gains
two methods at its end, so existing method indexes do not move. The gates
therefore cannot move through this diff. They are read in the host
sitting's own A/B cells. The host proof is that `run_inproc_e2e.sh` prints
the same pass lines as before this diff (§4 step 5).

## 3. Design

### DSP side

`dspq_bench_start(queue_id, mode)`:

1. If `dspqueue_import` is null, return `AEE_EUNSUPPORTED`. The symbol is
   declared `#pragma weak`, the SDK's own pattern
   (`examples/profiling/src/dspqperf_imp.c:22-26`).
2. `dspqueue_import(queue_id, NULL, NULL, NULL, &q)`. The callback is NULL
   because blocking reads are not allowed once a packet callback is set
   (`dspqueue.h`, `dspqueue_create` doc).
3. Start one `qurt_thread` with a 16 KiB `malloc` stack, at the caller's
   priority + 1 (as in `dspqperf_imp.c:78-91`).

The thread loop:

* Mode 0: `dspqueue_read(q, ..., 100000 µs)`. On `AEE_EEXPIRED` it
  re-checks a stop flag.
* Mode 1: spin on `dspqueue_read_noblock`, counting `AEE_EWOULDBLOCK` as
  empty polls, and re-check the stop flag every 4096 empties.

Packet handling:

* Request message: `{u32 op, u32 seq}`, where op 1 = echo and 2 = quit.
  The request carries 0 or 2 buffer references: `in` and `out`.
* For echo with 2 references, the thread copies 12 KiB from `in.ptr` to
  `out.ptr` (`memcpy`). The response carries `out` with `DEREF |
  FLUSH_SENDER | INVALIDATE_RECIPIENT`, plus `in` with `DEREF`. This is
  exactly the SDK example's pattern
  (`examples/dspqueue/src/dspqueue_sample_imp.c:283-288`).
* Response message: `{u32 seq, u32 status}`.
* A malformed packet increments `bad` and still gets a response, so the ARM
  side never hangs.

`dspq_bench_stop`:

1. Set the stop flag.
2. `qurt_thread_join`.
3. `dspqueue_close`.
4. Free the stack and fill `res`.

DSP heap: 16 KiB of stack, negligible against the 32-bit budget
(3840 MiB arena + ≈ 182 MiB heap, doc 46 §41).

### ARM side (one gtest binary, `DspqBench`)

**Symbol resolution.** Every `dspqueue_*` symbol is resolved with
`dlsym(RTLD_DEFAULT, ...)`, typed as `decltype(&dspqueue_create)` from
`$HEXAGON_SDK_ROOT/incs/dspqueue.h`. This follows the repo's precedent for
rpcmem (`htp_rpc_bench.h:44-73`, `htp_rpcmem.h`). The binary then has no
`dspqueue_*` NEEDED symbol, so it loads on a runtime without dspqueue and
still prints the FastRPC rows.

**Linking.** The SDK's `ipc/fastrpc/remote/ship/android_aarch64/libcdsprpc.so`
does export all 12 `dspqueue_*` symbols (checked with `nm -D`). Linking them
directly would therefore work. The dlsym route is chosen only so that
failure is loud but local, never a dynamic-linker abort.

**Session.** Open `nntr_hvx` on `&_dom=cdsp`, unsigned PD, as
`HtpFc::SetUp` does. Call `htp_set_latency_qos(h, env or 5000)`. Print
`DSPQ_BENCH env qos_mode=<0|1|2> poll_us=<n> ion=<y|n> mapped=<y|n>
signaling_perf=<n>`. `signaling_perf` comes from `dspqueue_get_stat(...,
DSPQUEUE_STAT_SIGNALING_PERF)`: 0 means the first implementation, 100 means
reduced signalling for polling clients, 1000 means optimized. It says which
runtime generation the numbers belong to.

**Buffers.**

* Two `HtpRpcBuffer(12288)` for the queue, each attached with
  `HtpRpcMemApi::mmap(CDSP_DOMAIN_ID, fd, p, 0, 12288, FASTRPC_MAP_FD)`.
  This is the mapping `htp_compute_ops.cpp:3599-3604` uses for the arenas.
* Three `HtpRpcBuffer(12288)` for `add_f32`.

**Rows.** Each row is 100 warm-up + 1000 timed round trips using
`steady_clock`. The row reports the median, p90, min and max of the sorted
samples.

| row | what | why |
|---|---|---|
| `F0` | `add_f32`, n = 32, plain heap | the bare invoke |
| `F12` | `add_f32`, n = 3072 (2 × 12 KiB in, 12 KiB out), ION | **(a)**: the reference for the decision |
| `Q{dsp}{arm}{pay}` × 8 | dsp ∈ {`B` blocking read, `S` spin}; arm ∈ {`B` `dspqueue_read` with 5 s timeout, `S` spin on `dspqueue_read_noblock`}; pay ∈ {`12` two buffer references: `in` with `REF \| FLUSH_SENDER \| INVALIDATE_RECIPIENT`, `out` with `REF`; `0` message only} | **(b)** in both signalling and polling mode, on each side; `pay=0` isolates the cache-maintenance share |
| `F12p` | `F12` again while the `S` thread is parked (queue open, idle) | the idle-cost proxy the bench can read (below) |

**Sequence.**

1. `F0`, `F12`.
2. Start with mode 0. Run `QBB12`, `QBS12`, `QBB0`, `QBS0`. Stop.
3. Start with mode 1. Run `QSB12`, `QSS12`, `QSB0`, `QSS0`, then `F12p`.
   Stop.

After each stop, print `DSPQ_BENCH dsp_stats mode=… served=… empty=…
bad=…`. Then print the verdict (§3, decision rule). Total run time is
estimated at under 30 s: 11 rows × 1100 round trips, even at 1 ms each.

**Idle cost of the parked thread.** Power is not readable from this
binary, and the plan does not claim it. What is readable:

* The `S` thread holds one DSP hardware thread at 100 % between packets.
  `empty` over the run's wall time shows it. It takes no HVX context.
* `F12p` vs `F12` shows whether a spinning thread slows the FastRPC path
  that stays for init and set_param.
* On the ARM side, `arm=S` spins one core. That is the same trade-off the
  5 ms `RPC_POLL_QOS` window already makes on every FastRPC call today, so
  it adds no new cost class.

A spinning DSP thread competing with the HVX worker pool during a stretch
is step 2's question. In step 2 the parked thread is the thread that runs
the stretch, and the level-2 profile's `dsp` column reads it.

### Loud failure

| condition | what prints | outcome |
|---|---|---|
| the device `libcdsprpc.so` lacks `dspqueue_*` | `DSPQ_BENCH unsupported side=arm sym=dspqueue_create` | `FAIL`; the `F*` rows are already printed |
| `dspqueue_create` returns `AEE_EUNSUPPORTED` / `AEE_EBADPARM` | `DSPQ_BENCH unsupported side=arm err=0x…` | `FAIL` |
| stale skel: `dspq_bench_start` returns `0x8000040e` | `(0x8000040e = stale skel, rule 3)`, the house string of `unittest_hvx_softmax.cpp:365` | `FAIL` |
| the DSP image has no dspqueue | `start` returns `AEE_EUNSUPPORTED` (the weak symbol is null): `DSPQ_BENCH unsupported side=dsp` | `FAIL` |
| missing symbols in the skel | a non-weak `dspqueue_*` import would stop the whole skel from loading (`0x80000406`), taking the production app down with it, so the `build.sh` guard forbids it | build exits 1 |

None of these conditions uses `GTEST_SKIP`. A skip is not a result.

### Host story

The in-process build has no FastRPC and no dspqueue, and a pthread queue
stand-in is step 2's work (issue step 2). **No functional host check is
possible for this bench.** The host can check four things:

1. The skel builds under `-Wall -Werror`, and the import guard shows
   exactly five new weak imports: `dspqueue_import`, `_close`, `_read`,
   `_read_noblock`, `_write`. Expected: `UNDEFINED SYMBOLS OK (51 runtime
   imports)`, where the baseline at `bb845426` is 46 (32 GLOBAL + 14 WEAK,
   measured by this planner).
2. The ARM binary builds with ndk-build, and `llvm-nm -D --undefined-only
   unittest_hvx_dspq | grep -c dspqueue_` prints `0` (the symbols are
   resolved through dlsym only).
3. `ninja -C build` and `run_host_checks.sh` pass after `generate_stub.sh`.
4. `run_inproc_e2e.sh` pass lines are unchanged.

The bench's statistics (sort, median, p90) are too small to need a host
test of their own. The verdict arithmetic is one line and is printed with
its inputs, so it can be re-checked by hand.

### Rejected alternatives

* **The SDK's `examples/profiling` dspqperf as a separate skel.** It
  already has `SYNC_POLL` and `SYNC_BLOCKED_READ` modes. It was rejected
  for two reasons. First, it runs in its own PD without this session's
  DCVS / apptype vote (`hvx_add_f32.c:126-176`) or the app's QoS, so its
  number would not be comparable with `F12` or the in-app transport. That
  would be a cross-condition reading, the thing LEDGER rule 23 warns about.
  Second, it would need its own skel build, push and signing path.
* **The framework packet callback on the DSP instead of a thread.** It was
  rejected because a callback cannot be the polling mode. Step 2 needs a
  thread that owns the stretch anyway.

### Decision rule

The bench prints the verdict with these definitions:

* T_F = `F12` median.
* T_Q = the `QSS12` median: bounded spin on both sides is the mode step 2
  would ship. The gaps between stretches are ARM ops of tens to hundreds of
  µs, far inside a spin window.
* Δ = T_F − T_Q.
* S(N) = N·Δ, the saving per token at N calls per token. Printed for N =
  95, 51, 3 and 1.

`QBB12` is printed beside it as the floor you get without spinning.

| Δ (µs) | S(51) | S(95) | verdict |
|---|---|---|---|
| **≥ 50** (T_Q ≤ ~35 at T_F ≈ 85) | ≥ 2.6 ms (≈ 9 % of today's 27.8 ms/token, ⅓ of the gap to 20 ms) | ≥ 4.8 ms | `adopt`: plan step 2 ahead of #132 PR 2. PR 2 stays held and is re-judged against the queue-on baseline, where it would save only ≈ 48·T_Q. |
| **< 25** (T_Q > ~60) | < 1.3 ms | < 2.4 ms | `drop`: close #141 with the numbers and release #132 PR 2. |
| 25 – 50 | 1.3 – 2.6 ms | 2.4 – 4.8 ms | `user`: `needs-user`. Recommendation: release PR 2 and park #141. PR 2 cuts the count itself (it saves ≈ 48·T_F ≈ 4.2 ms of transport plus ARM hook overhead). After PR 2, S(3) ≤ 0.15 ms, which is never worth a queue. |

Two cross-checks, both written into Notes:

1. **`F12` against the sitting's level-2 profile transport** (82–92 µs,
   rule 35). If `F12` ≪ the in-app transport, the remainder is staging
   outside the invoke, which a queue does not remove. Δ is then still the
   right quantity, and the S(N) figures are upper bounds.
2. **`QSS12` − `QSS0`** is the cache-maintenance share of the queue round
   trip. If it dominates, step 2 should use an uncached arena
   (`HTP_RPC_FLAGS_UNCACHED`, `htp_rpcmem.h`) rather than
   flush/invalidate flags.

## 5. Risks

**Host-vs-device gaps**

* **DVFS and C-states.** In `arm=B` rows the ARM thread sleeps. An idle
  gtest core parks deeper than a core inside a busy decode, so `QxB` rows
  are pessimistic and `QxS` rows are optimistic against the app. The
  decision uses `QSS12` because step 2 would spin. `QBB12` is printed so
  the no-spin cost is visible too. The DSP clocks come from the session's
  own vote (`hvx_add_f32.c:126-176`), the same vote in every row.
* **Thermal drift between sittings.** Everything is read inside one
  binary run, as a relative Δ. The absolute `F12` is compared only with
  the same sitting's profile transport. The zone0 temperature is recorded.
* **DMA rate.** The bench moves no weights, and the 12 KiB `memcpy` costs
  ≈ 1–2 µs, identical in the `F12` and `Q*12` rows. Not exposed.
* **Stale skel.** `0x8000040e` from `start` prints the rule-3 string. The
  handoff lists the skel md5 per stage, and `F0` / `F12` still print
  because `add_f32` has index 0.
* **Address-space budget.** The bench uses 16 KiB of DSP stack and two
  12 KiB `FASTRPC_MAP_FD` mappings, unmapped at the end. It does not touch
  the arena ceiling (doc 46 §39 / §41).

**Other risks**

* **Session or domain mismatch.** `dspqueue_create(CDSP_DOMAIN_ID, …)`
  binds to the domain's default session. `nntr_hvx_open` also uses the
  default `&_dom=cdsp` session, so the import lands in the same PD. A
  future multi-session setup would need the session's domain id.
  `dsp_stats served=` equal to the ARM count proves it for this run.
* **Runtime generation.** `signaling_perf` records whether this unit's
  dspqueue has the "reduced signalling for polling clients" path. A result
  from a 0-generation runtime is labelled as such, not generalised.
* **The SDK's own caveat** (`docs/software/ipc/dspqueue.html`, "Queue
  Depth"): dspqueue "is not designed to improve end-to-end latency for
  individual requests". Our use is exactly single-shot, synchronous, one
  packet in flight. That is why the bench measures before anything is
  adopted, and why `drop` is a real outcome.
