### 2.3 The conflicts, verified by a dry cherry-pick

`git merge-tree --write-tree origin/htp_decode archive/htp/185-dqr` and the
same against PR #203's head list the **same three code files** (plus the
contract doc, which is not ported). A scratch worktree at
`origin/htp_decode` took the 7 DQ commits with `cherry-pick -x`; two of
them stopped:

1. `dfd0242ec` × `htp_compute_ops.cpp:536–547` — two struct members added
   at the same spot. Keep both. Mechanical.
2. `b1a7c4cc0` × `hexkl_dma_ring.c:123–157`, `.h:121–154` — FSU's
   `hexkl_dcache_inva` and #177's `hexkl_dma_lane_push2d` / `_wait` appended
   at the same place. Keep both, **and** restore the `}` that closes
   `hexkl_dcache_inva` and the `/**` that opens the lane-push comment
   (the shared trailing lines belong to one side each; a marker-strip
   alone does not compile). Mechanical once that is known.

`a1a43a286`, `7da9d9d02`, `e05d032fd`, `7d0cb1517` and C3 `8dea5f0a7` then
apply clean. With the two fixes `run_host_checks.sh` on that worktree
printed `ALL CHECKS PASS` ×3, `GRAPH CHECKS PASS`, `TOKEN CHECKS PASS`,
`M1 FEED QUEUES TIMEOUT OK`. Port size: 17 files, +970 / −137.

No real design overlap was found, with one thing to prove on the host
rather than assume:

* **Per-lane queues × the pool's in-place rebind (PR #203).** A lane owns
  its descriptor chain only until its `hexkl_dma_lane_wait` returns, and
  every lane waits before its pool unit returns (plan 177 §3, the header
  comment). `graph_rebind` runs on the owner thread between kernel calls.
  So no descriptor can outlive the call that a rebind follows — the same
  guarantee the ring already relied on.
* **The feed's precondition "the caller's engine is idle at the first lane
  push".** The feed drains its own ring after the input copy. In the E2E
  graph (and in one PD, where the Q4 FC set shares S1) the op before a MoE
  op is an FC / norm on the same thread; any DMA it issued is waited
  before it returns. `run_inproc_e2e.sh` with the #185 scoreboards on is
  the check (step 3).
* **How the queue count reaches E0 / P28 / Q28.** `nntr_hvx_graph_env`
  copies `s->moe_flags` (set once by `moe_set_opts`) into the graph env,
  and `sendMoeOptsOnce` targets `HtpBackend::global().handle()`, which is
  `e2e_st_->h1` = S1 (`htp_compute_ops.cpp:1625,1640` on #203). The
  prefill's MoE calls send it before the first decode token. So
  `NNTR_MOE_DMA_QUEUES` applies to all four variants with no new wiring;
  the proof per run is the banner `applied=0x1f03e1` and `dmaq=4.00`.

Consumers of the changed contract: none in the IDL / stub (`nntr_hvx.idl`
unchanged, no `generate_stub.sh` rerun needed for this port — the stub is
rebuilt anyway because #203's IDL change is on the same device set);
`HtpComputeOps` (the env + `dmaq=` in the `[HTP-PROFILE]` line); the
quantizer, loader and `tools/htp_fc_report.py` are untouched (the format
tag does not move). `NNTR_HTP_PROFILE` gains `dmaq=` only.

**The user's note, "the S26 also looks like it runs without the DMA
optimization".** True on this tree: `htp_decode` has no
`NNTR_MOE_DMA_QUEUES`, so the M=1 feed issues every weight matrix from
one thread's queue, and on the v81 engine one queue reads ≈ 28–34 GB/s
where four read ≈ 62 (#177 G6). That is the −18..−22 % of #168 against
the S25 and the +22–25 % #177 won back. After the port the **default is
still one queue** (`HTP_MOE_DMA_QUEUES_DEFAULT 1u`): an unset run on the
S26 is the same "without" state, by design, so that the S25-measured rows
keep their meaning. The sitting therefore runs **one binary** and flips
only the env: `NNTR_MOE_DMA_QUEUES=4` against unset, same variant, same
half block; the 4-queue rows must show `applied=0x1f03e1`, `dmaq=4.00`,
`DMA_FIRST` ≈ 60 µs, the unset rows `0x703e1`, `1.00`, ≈ 130 µs. Whether
the default then flips to 4 (for v81 only, or for all) is the user's call
after the table (§7).

## 3. Design

**Chosen: cherry-pick the 7 DQ commits onto `htp_decode` as their own
branch `htp/204-s26-port`, resolve the three mechanical conflicts, then
rebase PR #203 onto it; the sitting runs #203's rebased head.** Reasons:
the conflicts are with `htp_decode` content (FSU, doc 52), identical
whether the target is `htp_decode` or #203; the port is small and host-
gated and should not sit under an unmerged review; the S26 re-baseline
needs Q28 (one PD), which only #203 has, so the sitting's tree is
"`htp_decode` + 204 + 203" either way. If #203 is not merged by the
sitting, the staged binary is built from `htp/201-pool-miss-path` rebased
onto `htp/204-s26-port` and the handoff records both heads; nothing else
changes.

C3 (DQR) is **not** ported by default: #185's ship rule chose DQ on the
S26 and C3 sits one clean cherry-pick away (`8dea5f0a7` applied without
conflict on the worktree). If the user wants the DQR read on the new unit
it is one extra variant knob — but it would be a skel difference, not an
env one, and breaks "one binary"; so it is a separate cell after this
sitting.

Rejected: **porting onto PR #203's branch first** (or squashing the sets
into #203). It couples a review-sized PR with a mechanical one, puts
the FSU-ring conflict resolution under a PR about the pool, and leaves
`htp_decode` itself unable to run the S26 at speed if #203 slips. Also
rejected: re-deriving the queue split by hand on the FSU ring — the dry
cherry-pick shows the kernel file is untouched on `htp_decode`, so there
is nothing to re-derive.

Contract §2 holds: no IDL change, no new wall, arena budget untouched
(the lanes' descriptors live in the existing scratch), no CPU fallback —
a lane timeout fails the call (`AEE_EFAILED`). Doc 45 §3: `_det` paths and
the activation handles are not touched; DMA stays behind compute (that is
what DQ is).

## 5. Risks

* **DMA rate per unit.** #177's 62 GB/s is one S26; this one may differ.
  The `DMA_FIRST` µs line on the two profile runs and the 4-vs-1 column
  make it visible without a cross-sitting compare.
* **Ceiling / address space.** The one-PD pool size (C = 29 on the S25)
  follows the PD space; the ceiling cell before the runs decides whether
  Q28 even loads. If it fails with `fastrpc_mmap(32 MiB)`, Q28 → Q24 and
  the table says so.
* **Thermal drift / DVFS.** Mirrored half blocks and the cool wait per
  block, zone0 ≤ 35 °C at each block start, pre / post temperature in the
  table; G=1024 not promised.
* **Stale skel / stub.** Two arches share a file name; `md5.txt` and the
  `ARCH OK (V81)` line in the staged log; #203's IDL change needs the
  rebuilt stub in the app (rung 3 `strings` count) — the `0x8000040e`
  symptom is listed in the handoff.
* **The default stays 1 queue.** Someone reading an unset S26 row as "the
  S26 number" reads the slow one. The table's queue column and the banner
  line guard it; the default flip is a user decision (§7).
* **Host-vs-device gap for the lane protocol.** The host stand-in has no
  queues; the scoreboards prove ordering, not that a blocked thread's queue
  keeps draining. #177's silicon result already covers the A path; the
  E2E / one-PD paths get their first silicon read here — a lane timeout
  shows as `AEE_EFAILED` on the token, never a hang.
