# 53. HTP MoE expert 플래시 스트리밍(cached-slim) 결과 정리

작성 2026-09-29 · 브랜치 `claude/eager-keller-f91z9o` · 상세 기록은 `52_flash_experts_on_htp_task.md` §10.28~§10.33

## 1. 요약

| 항목 | 내용 |
|---|---|
| 목표 | MoE expert 가중치를 전부 DRAM에 두는 상주 방식(물리 4.5 GiB) 대신, 일부만 DSP용 아레나에 두고 나머지를 flash에서 스트리밍해 메모리를 줄인다. ppl 불변, 속도는 상주에 최대한 가깝게 |
| 정확도 | 모든 구성·모든 실행에서 ppl **62.0916** (상주와 비트 동일) |
| warm prefill | C=8, C=16 모두 **상주와 같음** (606 / 592 vs 597 ms, 실행 편차 ±20 ms 안) |
| cold prefill | **flash 대역폭(3.0 GB/s) 바닥**에 붙어 있음. C=8 1.02 s, C=16 0.72 s. 앱에서 더 줄일 여지 없음 |
| decode | 캐시 미스 수에 묶임. C=8 17.9 TPS(상주 대비 −26%), C=16 21.7 TPS(−10%) |
| 결론 | 소프트웨어로 줄일 수 있는 비용은 다 줄였고, 남은 차이는 전부 "flash에서 읽는 바이트 수"에서 온다. 이것을 정하는 변수는 캐시 크기 C 하나이며, C는 메모리 예산이 정한다. 2.7 GiB가 허용되면 **C=16 권장** |

## 2. 측정 환경

| 항목 | 값 |
|---|---|
| 기기 | Android, Hexagon V79 HTP, cpu6–7 4.47 GHz / cpu0–5 3.53 GHz, UFS 실측 3.0 GB/s |
| 모델 | LFM2.5-8B-A1B, `lfm2.5-8b-a1b-q40-qs4cx-wh` (파일 4.3 GB) |
| MoE 구조 | MoE 층 22개 × expert 32개, top-4 라우팅. expert 1개 = gate_up 2048×3584 + down 1792×2048, int4, **5.25 MiB** |
| 입력 | 기본 프롬프트 444 토큰 prefill + 512 토큰 decode |
| 공통 설정 | `NNTR_NUM_THREADS=8`, 선읽기 기본값(리더 4개, 지평 = 풀이 허용하는 만큼) |
| 용어 | **C** = 층당 캐시 칸 수(`NNTR_MOE_CACHE_EXPERTS`). 풀은 22 × C칸을 22층이 공유. **warm** = 모델 파일이 OS page cache에 남아 있음, **cold** = page cache가 비어 flash에서 읽음 |

## 3. 최종 결과

### 3.1 성능 (최고 실측값)

**cold가 오프로딩의 정의에 맞는 상태다**: expert가 flash에만 있고 필요할 때 읽는다. warm은 직전 실행이 남긴 OS page cache(모델 파일 사본, 최대 4.3 GB, 회수 가능)에서 읽는 상태로, 그때의 실제 DRAM 사용은 보장 메모리 + page cache ≈ 6 GB다. 대표 수치는 cold, warm은 "여유 메모리가 있을 때"의 부가 정보.

| 구성 | 보장 메모리 | **prefill cold** (오프로딩 정의) | prefill warm (page cache 있을 때) | decode | ppl |
|---|---|---|---|---|---|
| **C=8** | 1.79 GiB | 1018 ms / **436.1 TPS** (1018~1043, 3회) | 606 ms / 732.7 TPS | **17.9 TPS** (17.8~18.4) | 62.0916 |
| **C=16** | 2.73 GiB | 718 ms / **618.4 TPS** (1회) | 592 ms / 750.0 TPS | **21.7 TPS** (21.6~21.8) | 62.0916 |
| 상주 (C=0) | 4.54 GiB | — (flash를 읽지 않음) | 597 ms / 743.7 TPS | **24.0 TPS** | 62.0916 |

### 3.2 메모리

| 구성 | 칸 수 | 앱 RSS | 아레나 (ION, RSS 밖) | **물리 합계** | C=8 대비 |
|---|---|---|---|---|---|
| C=8 | 176 | 873 MiB | 960 MiB | **1.79 GiB** | — |
| C=12 | 264 | 873 MiB | 1408 MiB | 2.23 GiB | +448 MiB |
| **C=16** | 352 | 873 MiB | 1920 MiB | **2.73 GiB** | +960 MiB |
| 상주 | 704 | 873 MiB | 3776 MiB | **4.54 GiB** | +2816 MiB |

- 칸 1개 = expert 1개 = WH 5.25 MiB + 스케일·colsum 44 KB, 4 KB 반올림 = 5.29 MiB. 아레나는 256 MiB 청크(칸 48개)로 잡는다.
- C가 1 늘 때마다 아레나 약 +116 MiB(22칸).
- **warm 성능은 OS page cache가 모델 파일(최대 약 4 GB)을 들고 있을 때의 값이다.** page cache는 회수 가능해서 앱 메모리에 잡히지 않지만, 메모리가 빠듯하면 OS가 먼저 버리고 그때 cold가 된다. 보장 메모리 기준의 정직한 수치는 cold다.

### 3.3 한계 효용

| 구간 | 추가 메모리 | cold prefill | decode | 1 GiB당 decode 개선 |
|---|---|---|---|---|
| C=8 → C=16 | +0.94 GiB | −300 ms | +3.8 TPS | **+4.0 TPS** |
| C=16 → 상주 | +1.81 GiB | −120 ms | +2.3 TPS | +1.3 TPS |

C=16 이후로는 들인 메모리 대비 효과가 3배 이상 떨어진다. decode 히트율이 57% → 85% → 100%로 포화되기 때문이다.

## 4. 이번 작업에서 바꾼 것

| # | 변경 | 결과 | 판정 |
|---|---|---|---|
| 1 | **등록을 offset만으로**: expert의 스케일·colsum을 아레나 칸에 WH 바로 뒤에 두고, DSP가 DMA로 가져간다. swap RPC 인자가 expert당 44 KB에서 offset 몇 개로 준다 | 등록 33.7 → **6.9 ms**, decode swap 토큰당 2.6 → 1.4 ms, warm prefill 상주 대비 +62 → **+9 ms** | 채택 |
| 2 | 리더 폭 제한: 앞선 배치는 리더 2개만 읽게 | 층 콜 경합은 줄었지만 end-to-end는 warm 630 vs 606, cold 1097 vs 988 ms로 둘 다 짐 | 기각, 코드 삭제 |
| 3 | flash 대역폭 측정 (`dd`) | 스트림 1/4/8개 모두 3.0 GB/s. 리더를 늘려도 이득 없음 | 근거 확보 |
| 4 | 선읽기 지평을 "풀이 허용하는 만큼"으로, 핀을 "뒤에 올 모든 층"으로 | C=16 cold 799 → **718 ms**. C=8은 변화 없음(1035 vs 1047 ms, 둘 다 528개 읽음) | 채택 |
| 5 | 기기 테스트 `HmxArenaSlotReuse.{Uncached,Swap,TailSwap}` | 3개 모두 통과, 같은 칸을 두 번째로 지날 때도 `bad_elems=0`. `Swap`의 기존 실패는 테스트 버그였음(재바인딩 뒤 옛 handle = 새 handle인데 release함) | 정확성 확인 |

## 5. 프로파일

측정 방법: `NNTR_HTP_PROFILE=2 NNTR_PPL=1`, 같은 세션(`tail.sh`), 상주 실행은 맨 뒤(상주의 큰 아레나가 page cache를 밀어내므로).

### 5.1 prefill 층 콜 1회 내부 (M>1, 23콜 평균, us/콜, warm)

| 구성 | host | dsp | transport | quant | gather | requant | dequant | acc | drain | push | scatter | alloc | stage | mm |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 상주 | 14354 | 13842 | 512 | 257 | 107 | 53 | 212 | 2947 | 234+41 | 49 | 29 | 19 | 380 | 9329 |
| **C=8 (현재, 리더 4)** | 15589 | 14525 | 1064 | 337 | 129 | 181 | 453 | 2957 | 164+29 | 61 | 98 | 22 | 452 | 9443 |
| C=8 (리더 2, 기각) | 14628 | 14180 | 448 | 298 | 168 | 114 | 326 | 2960 | 148+23 | 56 | 64 | 24 | 419 | 9392 |
| C=8 (등록 개선 전, §10.28) | 15845 | 14659 | 1186 | 314 | 212 | 178 | 448 | 2944 | 609+38 | 66 | 64 | 32 | 463 | 9096 |

읽는 법: 행렬곱(mm)과 누산(acc)은 구성과 무관하게 같다. 선읽기 리더가 아레나에 쓰는 동안 DDR을 많이 쓰는 단계(quant·requant·dequant·scatter)와 transport만 느려진다. 이것이 리더의 DDR 경합이며 콜당 약 +1.2 ms × 23콜 ≈ 28 ms다.

### 5.2 decode 층 콜 1회 내부 (M==1, 11264콜 평균, us/콜)

| 구성 | host | dsp | transport | quant | gather | acc | drain | mm |
|---|---|---|---|---|---|---|---|---|
| 상주 | 1455 | 1371 | 84 | 15 | 127 | 259 | 115+36 | 790 |
| C=8 | 1408 | 1331 | 78 | 18 | 115 | 259 | 87+33 | 790 |

decode 콜 자체는 두 구성이 같다. C=8의 decode 차이는 콜 밖의 미스 처리(5.4)에서 온다.

### 5.3 expert I/O (C=8)

| 항목 | warm, 리더 4 (현재) | warm, 리더 2 | §10.28 (개선 전) | cold, 현재 |
|---|---|---|---|---|
| prefill 선읽기 expert 수 | 528 | 528 | 528 | 528 |
| 층이 요청할 때 이미 읽힌 비율 | 100% | 100% | 100% | 58~59% |
| 노출 대기 (읽기를 기다린 시간) | 0.5 ms | 0.5 ms | 0 | **340 ms** |
| 리더 1개의 expert 1개 읽기 | 2.11 ms | 1.42 ms | — | 6.7~6.9 ms |
| prefill 등록 RPC 합 | **7.0 ms** | 6.9 ms | 33.7 ms | 7.5 ms |
| decode 미스 | 19285 (1.71/콜) | 19285 | 19285 | 19285 |
| decode 미스 읽기 | 0.37 ms/미스 | 0.35 ms/미스 | 0.32 ms/미스 | 0.31 ms/미스 |
| decode swap RPC 합 (512토큰) | 702 ms | 697 ms | 1347 ms | 706~716 ms |
| 로드 시 등록 (prefill 밖) | 3006 ms | 3108 ms | — | — |

cold에서 리더 4개의 합산 읽기 속도는 4 × 5.25 MiB ÷ 6.7 ms = 3.3 GB/s로 flash 상한에 닿는다.

### 5.4 decode 토큰 1개 분해 (C=8)

| 구성 요소 | ms/토큰 | 근거 |
|---|---|---|
| 상주와 같은 계산 | 41.6 | 1000 / 24.05 TPS |
| 미스 읽기 | 13.1 | 0.35 ms × 37.6개 (1.71/층 × 22층) |
| swap RPC | 1.4 | 697 ms / 512 토큰 |
| **합계** | **56.1** | → 17.8 TPS (실측 17.9) |

### 5.5 flash 대역폭 (`dd`, evict 뒤, 같은 구간을 두 번 읽어 cold/warm 구분)

| 측정 | 읽은 양 | 시간 | 대역폭 |
|---|---|---|---|
| 8스트림 × 256 MB, cold | 2 GB | 0.69 s | **3.0 GB/s** |
| 같은 8스트림, warm | 2 GB | 0.19 s | 11 GB/s |
| 4스트림 × 512 MB, cold | 2 GB | 0.69 s | **3.0 GB/s** |

### 5.6 cold prefill 바닥 산술

| 구성 | prefill 중 flash에서 읽는 expert | 바이트 | ÷ 3.0 GB/s | + 층 0 | 실측 |
|---|---|---|---|---|---|
| C=8 | 22 × (32 − 8) = 528 | 2.91 GB | 0.97 s | ~1.0 s | 1.02~1.04 s |
| C=16 | 22 × (32 − 16) = 352 | 1.94 GB | 0.65 s | ~0.68 s | 0.72 s |

prefill은 444토큰을 한 콜에 처리하므로 층마다 32개 expert가 전부 필요하다. 미리 올려 둔 22 × C개를 뺀 나머지는 앞 층이 칸을 비운 뒤에야 들어갈 수 있어서, 반드시 prefill 도중에 읽어야 한다. prefill 시간 ≈ max(flash 읽기, DSP 계산 0.6 s)다.

### 5.7 캐시 교체 정책 시뮬레이터 (C=8, decode trace 11264콜)

| 정책 | 히트 % | TPS (보정 산술) |
|---|---|---|
| ours (현재) | 57.2 | 17.96 |
| lfu | 59.1 | 18.2 |
| lrfu:32 (실현 가능한 최선) | 59.6 | 18.2 |
| belady (미래를 아는 상한) | 78.5 | 20.7 |
| C=12 ours / belady | 72.7 / 88.5 | 19.9 / 22.4 |

정책을 바꿔도 +2.4%p(+0.26 TPS)로 채택 기준(3%p)에 못 미친다. C=8에서 상주 decode는 어떤 정책으로도 불가능하다.

## 6. best를 정한 논리

1. **남은 차이가 소프트웨어 탓인지 물리 한계인지 가른다.** 기준은 "실측이 산술 바닥에 붙어 있는가"다.

   | 지표 | 산술 바닥 | 실측 | 판정 |
   |---|---|---|---|
   | warm prefill | 상주 597 ms | 606 ms | 끝남 (편차 안) |
   | cold prefill C=8 | ~1.0 s | 1.02 s | 바닥 |
   | cold prefill C=16 | ~0.68 s | 0.72 s | 바닥 |
   | decode C=8 | 56 ms/토큰 | 56 ms/토큰 | 바닥 |

   전부 바닥에 붙어 있으므로 코드로 더 줄일 것이 없다. 남은 차이는 모두 flash에서 읽는 바이트 수이며, 그것을 정하는 변수는 C 하나다.
2. **C는 메모리 예산이 정한다.** 1.8 GiB면 C=8, 2.7 GiB면 C=16, 4.5 GiB면 상주.
3. **한계 효용이 C=16 근처에서 꺾인다**(3.3). 그래서 예산이 허용하면 C=16이 가장 효율적이다.

## 7. 검토했지만 기각한 안

| 안 | 기각 근거 |
|---|---|
| 리더 수 늘리기 | flash가 스트림 수와 무관하게 3.0 GB/s |
| 리더 폭 제한 | 실측으로 warm·cold 모두 느림 (4번 표) |
| 모델 파일을 page cache에 미리 채우기 | page cache 약 3.7 GB 추가. C=8 + 3.7 GB는 상주보다 메모리를 더 쓰고 decode는 느리다 |
| `O_DIRECT`로 flash → 아레나 직접 | dma-buf 매핑은 페이지 고정이 안 될 가능성이 크고, 되더라도 상한은 같은 3.0 GB/s |
| 가중치 압축 | int4 엔트로피 약 3.6비트, 10% 절감을 CPU 디코딩이 먹음 |
| prefill에서 expert 일부 건너뛰기 | ppl이 바뀜 |
| 캐시 교체 정책 변경 | 시뮬레이터 +2.4%p, 기준 미달 (5.7) |
| decode 선읽기 (직전 토큰 top-k) | 상한 64%, 헛읽기가 DDR을 더 씀 |

## 8. 남은 일 / 미확인 항목

- **C=16 cold는 1회 측정.** 보고용으로 두 번 더 재서 확인 필요. C=16의 352개 선읽기도 산술 값이고 프로파일로 확인하지 않았다.
- **decode 최적화**(히트 expert 계산과 미스 읽기를 한 층 안에서 겹치기 등)는 별도 담당자가 진행 중.
- 기기 테스트 `HmxMmU8I4Layer.MoeLayerSplitMatchesWhole`(C=1 split의 ppl 차이 원인) 미실행.

## 9. 재현 방법

```bash
# 빌드·설치 (앱만; skel은 test/htp/build.sh로 따로)
cd Applications/CausalLM
HEXAGON_SDK_ROOT=<SDK> HEXKL_ROOT=<HexKL> ./build_android.sh --htp && ./install_android.sh

# 실행 (C=8 또는 16)
adb shell 'cd /data/local/tmp/nntrainer/causallm && LD_LIBRARY_PATH=. ADSP_LIBRARY_PATH=. \
  NNTR_NUM_THREADS=8 NNTR_MOE_CACHE_EXPERTS=16 ./nntrainer_causallm ./models/lfm2.5-8b-a1b-q40-qs4cx-wh'
```

| 환경변수 | 기본값 | 의미 |
|---|---|---|
| `NNTR_MOE_CACHE_EXPERTS` | 0 (상주) | 층당 캐시 칸 수 C |
| `NNTR_MOE_PREFETCH` | 풀이 허용하는 만큼 | prefill 선읽기 지평(층 수). 0이면 끔 |
| `NNTR_MOE_PREFETCH_READERS` | 4 | 선읽기 리더 스레드 수 |
| `NNTR_HTP_PROFILE` | 0 | 2면 층 콜 단계별 프로파일 출력 |
| `NNTR_PPL` | 0 | 1이면 프롬프트 ppl 출력 |

- cold 측정은 다른 큰 모델을 한 번 돌려 page cache를 비운 뒤에 한다. 비워진 정도에 따라 ±100 ms 흔들리므로 여러 번 재서 가장 느린 쪽(완전 cold)을 쓴다.
- warm 측정은 같은 구성을 한 번 돌린 직후에 한다.
