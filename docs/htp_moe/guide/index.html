What the project is

The project runs the language model LFM2.5-8B-A1B on a Galaxy S25 Ultra (Snapdragon 8 Elite) and moves the heaviest part of every step onto the phone's signal processor (the Hexagon HTP, Qualcomm's name for the NPU built around a DSP). The model has 24 layers — 18 "conv" layers and 6 attention layers — and 22 of them carry a mixture-of-experts feed-forward block (MoE FFN): 32 small expert networks of which every token uses only 4. Hidden width is 2048, the vocabulary 128 000 words, and the output projection (lm_head) is tied to the input embedding. contract §1, model row (from the model's config.json)

The starting point is an upstream pull request (nntrainer PR #4327) that already runs the MoE FFN on the HTP and wins at prefill — reading the prompt, many tokens at once. This guide is only about decode: producing one new token at a time, where the NPU path started out slower than the CPU. The goal: decode at ≥ 50 tokens per second on the NPU at every generation length, which is about 2.4× the PR's own NPU number (20.8) and above the phone's CPU. Since the record sitting of 2026-09-30 the NPU path decodes at 53.97 / 52.16 / 51.41 tok/s at gen 64 / 512 / 1024 on a cool start (each length started with the phone below 35 °C), on the second phone R3CY10WM83Y, and the CPU control on the same phone under the same protocol reads 52.18 / 51.31 / 50.12 — the goal is met, and the NPU is ahead of the CPU by 1.7–3.4 %, narrowly. A warm start still reads 47–49 at gen 1024. The step that got it there was one bit on the DSP's weight DMA (#158, 2026-09-29): reading the expert weights past the DSP's L2 cache took the DMA from ≈ 33 to ≈ 57 GB/s and decode from ≈ 37 to ≈ 51 tok/s, with every output byte unchanged. Every speed-up since 2026-09-28 must leave the generated text identical to the switch-off baseline (the direction change). Since 2026-09-30 the work is on the base branch htp_decode and aims at the end-to-end path — every decode op on the DSP, one call per token — which is bit-preserving but at 43–47 tok/s still slower than the default it would replace. contract §1 "Now" and "Goal" rows (cycle 30: the record sitting; user decision Q1 ii); record-2026-09-30-cool-a.md Verdict; 158-dma-bypass.md; BENCHMARK Results (#201 one-PD, #207 rows); earlier: BENCHMARK.md "Goals", NPU row, and Method (the cycle-21 paragraph); 141-dspq-moe.md @ 4049dd15 Results (tok/s table, Gates); contract §12 (2026-09-28, direction change)

The one-paragraph mental model

One token = read ≈ 886 MB of weights. During decode there is one token, so every matrix multiply is a matrix times a single vector. Arithmetic is nearly free; what costs time is pulling every weight byte the token touches out of the phone's main memory (DDR). On the NPU path that is about 886 MB per token: the 4 active experts in each of 22 MoE layers (484 MB, in the NPU's QS4CX_WH format), the dense Q4_0 projections — conv in/out, attention q/k/v/o and the dense FFN of layers 0–1 — (≈ 255 MB), and the tied lm_head (147 MB). The project started from doc 48's 730 MB; cycle 21 recounted it from config.json and checked it against both model files to 0.2 % (LEDGER rule 42). The same recount changed the ceiling story: the CPU control reads ≈ 947 MB per token at 52.4 tok/s, i.e. ≈ 50 GB/s, so the old line "34–38 GB/s ⇒ 48–52 tok/s, and the CPU already sits on it" was an arithmetic artefact. At 50 tok/s a token has 20 ms. To get there the DSP must (1) read its share of the weights as fast as the memory lets it and (2) cost next to nothing to call — and the CPU must read the rest fast too.

(1) is done — and the floor turned out to be higher than cycle 21 thought. The vector-unit path (GEMV) that replaced the matrix unit for decode at first read its 22 MB of weights per call straight out of DDR and spent ≈ 74 % of its time waiting for them (#105). Since PR #118 the DSP's DMA engine copies the next expert's weights into on-chip memory (VTCM) while the vector unit works on the current one (#117, #120). In cycle 21 the engine looked pinned at ≈ 33 GB/s in the app (rule 41). #158 found the reason: the DMA read its source through the DSP's L2 cache. With src_bypass=1 on the expert weight descriptors the isolated rate went 37.3 → 69.3 GB/s and the in-app ring 31.5–33.4 → 56.3–57.9; the MoE call fell 726 → 418 µs, the MoE wait per token 16.1 → 9.85 ms, decode +31–35 %, bit-identical (rule 43; the default since 21169f6e). (2) is done too. Each ARM↔DSP call cost ≈ 0.5 ms at the start; #88 cut it to 0.09 ms and #141's dspqueue to 14.1 µs (rule 40). What is left is the CPU, and it is near its byte floor. Measured per op (NNTR_OP_TIME=1), a gen-512 token is 19.74 ms = MoE wait 9.85 + ≈ 9.9 on the CPU, which streams the Q4_0 projections at 51–63 GB/s (rule 46); the phone's DRAM tops out at ≈ 70 GB/s for any mix of readers, so a second reader only redistributes bandwidth (rule 44, #90), and neither CPU-side lever tried at gen 1024 paid (rule 51). At gen 1024 a cool-start token is 19.1–19.7 ms — just inside 20 — which is why the start temperature decides that cell (rule 52). The end-to-end path removes the CPU's share by moving it onto the DSP: one PD holding the projections, lm_head and a 28-of-32 expert pool reads 22.4 ms a token today (rule 59); its expert misses are the term #216 and #219 work on.

Why the NPU was slow — three walls: all three have fallen, and a fourth (the DSP L2 on the DMA source) with them

The PR's own device work measured one MoE layer call at decode: 1.91 ms on the host, of which 1.35 ms is DSP work and 0.57 ms is the ARM↔DSP round trip. Three things hide in that number, and all three must fall (see page 2):

  1. The matrix unit computes 64 rows for 1 row. The HMX tile is 64 rows tall; decode has one row, so 63/64 of the work is padding: 1.03 of the 1.35 ms. Fix: a vector-unit (HVX) matrix-vector kernel (GEMV) for M ≤ 4 — built (PR #86), measured (#94 sitting 2: decode +6.2 / +7.7 / +1.7 %, text identical) and the default since PR #108 (merged 2026-09-22; NNTR_MOE_HTP_M1_GEMV=0 turns it off). The padding is gone, but the GEMV reads the 22 MB of weights per call straight from DDR at ≈ 22.6 GB/s, and #105 measured that ≈ 74 % of its time is waiting for those bytes: a cheaper inner loop (PR #107) is 2.26× faster when the weights are already in cache and no faster from DDR. #100 (2026-09-23) then measured the alternative — DMA the weights into the DSP's on-chip memory (VTCM) — at 31.6 GB/s, only ≈ 1.2× the direct read, on a day when the same phone's DMA ran 22 % slower than the day before on an untouched test cell. The user's direction after that: stop leaning on DMA numbers, take the compute-side wins. The wait is DDR latency (rule 26), and the one knob measured against it, the l2fetch prefetch lead, kept helping up to the largest value tried (192 KB) and was never tried on the loop the phone runs by default. #113 measured that whole loop × lead matrix on 2026-09-23 (one skel, one app, the loop and the lead picked by two environment variables): the four-row loop is harmed by any lead, 2.1–2.5× on the arena and unchanged when the weights are already in cache — the prefetch competes with the loop's own loads, it does not evict anything (rule 31) — and only the one-row loop gains, only up to 192 KB. That best cell, D192, reads mm 937.0 µs against 1000.2 (−6.3 %; the 840 µs gate is missed on every cell and nothing unmeasured could pass) yet decodes +4.11 / +3.29 / +4.26 % faster with byte-identical text, so the user landed it as the default anyway (rule 33, PR #115); PR #107 closed with its machinery kept. The compute side of the GEMV is exhausted: under a direct DDR read mm cannot go below ≈ 815 µs. The ride-along settled the other half: the DMA cell nobody touched read 31.2 GB/s on a cold phone, the same as #100, so 31–32 GB/s is that unit's DMA bound (rule 32) and the VTCM feed is worth ≈ 1.33× there. #117 built and measured it (2026-09-23, on the user's second S25 Ultra): each expert's two weight matrices are DMA'd into VTCM one expert ahead, into two slabs that alternate by expert, and the one-row loop reads the copy with its lead switched off. mm 931.9 → 676.4 µs (gate ≤ 760, passed in a warm and in a cooled sitting), the engine busy 90 % of the call at 32–34 GB/s, decode +32.5 / +30.9 / +28.6 % with byte-identical text in 36 of 36 runs, prefill untouched (the feed runs only at M = 1). Landed by the gate: PR #118 makes the feed the default (feed=vtcm in the banner; NNTR_MOE_HTP_GEMV_FEED=0 is the opt-out). The new fact under it: that phone's DMA engine reads 37.3 GB/s on the anchor cell against 31.2 on the earlier unit while its vector unit reads DDR at the same rate, so the feed's win is unit-dependent — ≈ +10 % projected on the slower phone (rule 34). What is left inside the call is ≈ 1.9 ms per token of engine gap on a fast unit (㉓, in-situ 32–34 vs 37.3), nothing on a slow one. #120 (2026-09-23, same unit) ran the flipped default as its own sitting's control: A 35.97 / 35.96 / 35.17 against A0 (feed off) 28.62 at G=64, +25.7 %, mm 677.2 vs 934.3, text identical — so the feed is confirmed as a control, ㉒ is closed, and the ring line reads engine 32.3..34.4 GB/s again, so the ㉓ gap is real on this unit. See page 2 §2.2 e′.
  2. Weight DMA at 16–18 GB/s — dissolved as a descriptor-list problem (#100). Inside the old (HMX) layer call the DMA averaged 16–18 GB/s while the same engine reached 72–117 GB/s in an isolated probe, and #94 sitting 2 had located most of the gap in the call's own 46-descriptor list ("row h": replayed with no compute it did 40 GB/s where a probe of the same shape did 107). #100 measured the probe against a per-call cell whose content is checked (c_star): that validated ceiling is 26.3 GB/s, and the real list runs at 1.19× it — faster than the ceiling, so there was never a list-side loss to fix; the probe number was one no real per-call path can reproduce (rule 28; rule 11 amended, rule 19 withdrawn). The engine tops out near 31 GB/s on every validated cell whatever the descriptor count or shape. With the GEMV the default, the list is not on the decode path anyway (2 descriptors per call). What remains of wall 2 at decode is the read rate itself, which lives in wall 1's prefetch question.
  3. The round trip — closed on 2026-09-22 (#88). It cost 401 µs per call in #88's own control run (22 calls per token). Most of that was not the arguments (464 bytes per call) but two things: (a) the activation and output buffers had grown to the prompt's size, 4 MiB each, and the FastRPC driver keeps a whole cached buffer consistent between ARM and DSP on every call — so every decode call paid for flushing 4 MiB although it used 8 KiB; (b) the ARM waited for the answer by polling (spinning on a flag) for only 100 µs, and a 1.4 ms call always outlived that and fell back to the slower interrupt wake-up. Upstream's size-class staging (a 64 KiB buffer for decode) and a 5 ms poll window, merged as PR #103, took the transport to 87.9 µs per call (−78 %): 245.8 µs of the cut is the staging, 67.6 µs the poll. Decode rose +30.9 / +41.4 / +42.9 %, text identical, prefill −0.9 % (inside the −5 % gate). On the GEMV path #100 read the two paths in one sitting on one binary: 185.8 µs (GEMV) vs 84.6 (HMX) per call, +101 µs, with the same 64 KiB buffers — and the ledger booked it as the price of the path, to come back only with one call per token. That reading was wrong (rule 35): under #117's VTCM feed, the same binary and sitting read 190 → 92 µs per call, the HMX path's level — the extra transport belonged to the direct HVX read of the arena, not to the GEMV path, and ≈ 2.2 ms per token came back with the feed. Cause not separated (the arena read may leave the ARM-side cache maintenance or the dmlink sync more to do at the call boundary; the shorter call stays inside the poll window). Transport is ≈ 1.8 ms per token at the feed default (#120 A: 82.2 µs × 22; #117 B had read 92 µs); the rest of it goes only with one call per token — whose IDL skeleton landed as PR #119 (merged 2026-09-23, NNTR_HTP_FORWARD=1, off by default) and, with only the MoE op resident, still makes 22 calls per token; the kernels for the other five kinds landed on 2026-09-27 (PRs #125, #126) but are not in the table — that is #130. Cycle 21 took the rest of it (#141, PR #151, default since 2026-09-28): the 22 MoE calls now ride a dspqueue — a shared-memory message queue that a DSP thread watches, spinning for up to 1 ms between calls — instead of a FastRPC invoke. A microbench on the phone read 87.1 µs per FastRPC round trip against 16.7 µs through the queue with both sides spinning (PR #147); in the model the transport fell 87.9 → 14.1 µs per call (0.3 ms per token), MoE outputs bit-identical, decode +7.1 / +5.0 % at gen 64 / 512 (LEDGER rule 40).

A fourth limit sat inside wall 2 unseen until 2026-09-29: the DMA engine read the arena through the DSP's L2 cache. Setting the source-bypass bit on the expert weight descriptors (#158) took the in-app rate from ≈ 33 to ≈ 57 GB/s and decode +31–35 %, bit-identical — the default since 21169f6e. 158-dma-bypass.md; LEDGER rule 43
