What "2-bit experts" and "ternary" mean for decode. A ternary weight is one of three values, −1, 0 or +1, times a scale stored once per output column. Three values fit in 2 bits, so an expert weight can be stored in a quarter of a byte instead of half a byte. Decode speed is set by the bytes a token reads (next section), so this matters directly: on Gemma's shape the experts' bytes per token halve, 714 → 357 MB, and plan 229's byte floor at ≈ 70 GB/s moves from 34 to 45 tok/s with the experts at 2 bits (61 if the attention and dense projections went to 2 bits as well, which needs work not yet built). The format, QS2CX_WH (from upstream PR #4410), keeps four 4-bit values per tensor — a palette — and stores for every weight a 2-bit index into it; ternary uses three of the four. At decode the kernel never unpacks the weights to memory: it reads the packed codes, looks each pair of codes up in a 16-entry table held in a register, and multiplies the resulting 4-bit values exactly as the 4-bit kernel does. Because the looked-up values are the same 4-bit numbers, the output is bit-identical to the 4-bit "palette twin" (the same model stored at 4 bits with only those four values used). Details and a diagram: page 2 §2.8. Since 2026-10-07 the storage format is pinned (#229 S0 closed): experts at 2 bits in 32 × 32 tiles with a per-column scale, values {−2, −1, 0, +1} (ternary plus a rare −2), everything else Q4_0. The user's file holds the codes in a different order inside each tile and has no palette, so a tool of ours rewrites it into QS2CX_WH (tools/htp/repack_int2_to_qs2cx.py, #250; page 2 §2.8); the real checkpoint will take the same tool. What the project is

The project runs the language model LFM2.5-8B-A1B on a Galaxy S25 Ultra (Snapdragon 8 Elite) and moves the heaviest part of every step onto the phone's signal processor (the Hexagon HTP, Qualcomm's name for the NPU built around a DSP). The model has 24 layers — 18 "conv" layers and 6 attention layers — and 22 of them carry a mixture-of-experts feed-forward block (MoE FFN): 32 small expert networks of which every token uses only 4. Hidden width is 2048, the vocabulary 128 000 words, and the output projection (lm_head) is tied to the input embedding. contract §1, model row (from the model's config.json)

The one-paragraph mental model

(For Gemma-4-26B-A4B the same count is ≈ 2.05 GB a token at 4 bits, and 2-bit experts take 357 MB off it — plan 201 §3, plan 229 §3.2. The LFM2.5 numbers below are the measured ones.)

One token = read ≈ 886 MB of weights. During decode there is one token, so every matrix multiply is a matrix times a single vector. Arithmetic is nearly free; what costs time is pulling every weight byte the token touches out of the phone's main memory (DDR). On the NPU path that is about 886 MB per token: the 4 active experts in each of 22 MoE layers (484 MB, in the NPU's QS4CX_WH format), the dense Q4_0 projections — conv in/out, attention q/k/v/o and the dense FFN of layers 0–1 — (≈ 255 MB), and the tied lm_head (147 MB). The project started from doc 48's 730 MB; cycle 21 recounted it from config.json and checked it against both model files to 0.2 % (LEDGER rule 42). The same recount changed the ceiling story: the CPU control reads ≈ 947 MB per token at 52.4 tok/s, i.e. ≈ 50 GB/s, so the old line "34–38 GB/s ⇒ 48–52 tok/s, and the CPU already sits on it" was an arithmetic artefact. At 50 tok/s a token has 20 ms. To get there the DSP must (1) read its share of the weights as fast as the memory lets it and (2) cost next to nothing to call — and the CPU must read the rest fast too.

(1) is done — and the floor turned out to be higher than cycle 21 thought. The vector-unit path (GEMV) that replaced the matrix unit for decode at first read its 22 MB of weights per call straight out of DDR and spent ≈ 74 % of its time waiting for them (#105). Since PR #118 the DSP's DMA engine copies the next expert's weights into on-chip memory (VTCM) while the vector unit works on the current one (#117, #120). In cycle 21 the engine looked pinned at ≈ 33 GB/s in the app (rule 41). #158 found the reason: the DMA read its source through the DSP's L2 cache. With src_bypass=1 on the expert weight descriptors the isolated rate went 37.3 → 69.3 GB/s and the in-app ring 31.5–33.4 → 56.3–57.9; the MoE call fell 726 → 418 µs, the MoE wait per token 16.1 → 9.85 ms, decode +31–35 %, bit-identical (rule 43; the default since 21169f6e). (2) is done too. Each ARM↔DSP call cost ≈ 0.5 ms at the start; #88 cut it to 0.09 ms and #141's dspqueue to 14.1 µs (rule 40). What is left is the CPU, and it is near its byte floor. Measured per op (NNTR_OP_TIME=1), a gen-512 token is 19.74 ms = MoE wait 9.85 + ≈ 9.9 on the CPU, which streams the Q4_0 projections at 51–63 GB/s (rule 46); the phone's DRAM tops out at ≈ 70 GB/s for any mix of readers, so a second reader only redistributes bandwidth (rule 44, #90), and neither CPU-side lever tried at gen 1024 paid (rule 51). At gen 1024 a cool-start token is 19.1–19.7 ms — just inside 20 — which is why the start temperature decides that cell (rule 52). The end-to-end path removes the CPU's share by moving it onto the DSP: one PD holding the projections, lm_head and a 28-of-32 expert pool reads 22.4 ms a token today (rule 59); its expert misses are the term #216 and #219 work on.

Why the NPU was slow — three walls: all three have fallen, and a fourth (the DSP L2 on the DMA source) with them

The PR's own device work measured one MoE layer call at decode: 1.91 ms on the host, of which 1.35 ms is DSP work and 0.57 ms is the ARM↔DSP round trip. Three things hide in that number, and all three must fall (see page 2):

  1. The matrix unit computes 64 rows for 1 row. The HMX tile is 64 rows tall; decode has one row, so 63/64 of the work is padding: 1.03 of the 1.35 ms. Fix: a vector-unit (HVX) matrix-vector kernel (GEMV) for M ≤ 4 — built (PR #86), measured (#94 sitting 2: decode +6.2 / +7.7 / +1.7 %, text identical) and the default since PR #108 (merged 2026-09-22; NNTR_MOE_HTP_M1_GEMV=0 turns it off). The padding is gone, but the GEMV reads the 22 MB of weights per call straight from DDR at ≈ 22.6 GB/s, and #105 measured that ≈ 74 % of its time is waiting for those bytes: a cheaper inner loop (PR #107) is 2.26× faster when the weights are already in cache and no faster from DDR. #100 (2026-09-23) then measured the alternative — DMA the weights into the DSP's on-chip memory (VTCM) — at 31.6 GB/s, only ≈ 1.2× the direct read, on a day when the same phone's DMA ran 22 % slower than the day before on an untouched test cell. The user's direction after that: stop leaning on DMA numbers, take the compute-side wins. The wait is DDR latency (rule 26), and the one knob measured against it, the l2fetch prefetch lead, kept helping up to the largest value tried (192 KB) and was never tried on the loop the phone runs by default. #113 measured that whole loop × lead matrix on 2026-09-23 (one skel, one app, the loop and the lead picked by two environment variables): the four-row loop is harmed by any lead, 2.1–2.5× on the arena and unchanged when the weights are already in cache — the prefetch competes with the loop's own loads, it does not evict anything (rule 31) — and only the one-row loop gains, only up to 192 KB. That best cell, D192, reads mm 937.0 µs against 1000.2 (−6.3 %; the 840 µs gate is missed on every cell and nothing unmeasured could pass) yet decodes +4.11 / +3.29 / +4.26 % faster with byte-identical text, so the user landed it as the default anyway (rule 33, PR #115); PR #107 closed with its machinery kept. The compute side of the GEMV is exhausted: under a direct DDR read mm cannot go below ≈ 815 µs. The ride-along settled the other half: the DMA cell nobody touched read 31.2 GB/s on a cold phone, the same as #100, so 31–32 GB/s is that unit's DMA bound (rule 32) and the VTCM feed is worth ≈ 1.33× there. #117 built and measured it (2026-09-23, on the user's second S25 Ultra): each expert's two weight matrices are DMA'd into VTCM one expert ahead, into two slabs that alternate by expert, and the one-row loop reads the copy with its lead switched off. mm 931.9 → 676.4 µs (gate ≤ 760, passed in a warm and in a cooled sitting), the engine busy 90 % of the call at 32–34 GB/s, decode +32.5 / +30.9 / +28.6 % with byte-identical text in 36 of 36 runs, prefill untouched (the feed runs only at M = 1).
