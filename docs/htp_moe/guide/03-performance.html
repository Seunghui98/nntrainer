What it means, in plain words. Every decoded token makes 22 calls from the ARM into the DSP, one per MoE layer. Until now each was a FastRPC call: the kernel driver marshals the arguments, wakes a DSP thread, runs the function and wakes the ARM again — 87.9 µs of pure transport per call on this phone, ≈ 1.9 ms per token. A microbench in the #134 sitting (PR #147) had measured the alternative, the SDK's dspqueue: a shared-memory message queue that a DSP thread watches. With both sides spinning (checking the queue in a tight loop) a round trip carrying the same 12 KiB took 16.7 µs against FastRPC's 87.1. #141 step 2 moved the model's 22 M==1 MoE calls onto such a queue while running the same DSP function on the same argument bytes, so nothing the DSP computes could change — and on the phone nothing did: every one of 2862 MoE dump files is bit-identical to the FastRPC run, and all eight prompts of the new text set produce the same text. The transport fell to 14.1 µs per call and decode rose +7.1 % at gen 64 and +5.0 % at gen 512. Letting the DSP thread sleep between calls instead (Q0) kept only part of it — the 1 ms spin window is what buys the latency. The user made it the default (PR #151, NNTR_HTP_DSPQ=0 brings FastRPC back). Why this moves the "now" without a control sitting, unlike #117's feed: the change is bit-identical to A at every MoE call, so a control sitting could only re-read the transport this sitting already read as an A/B; the flip commit changes nothing but the unset value of the switch, and its banner was checked on the phone. What it leaves: the MoE call now has ≤ 0.9 ms left in it (the dsp − mm tail and the transport); the weights run at the in-app DMA floor (#149, rule 41). The other ≈ 10.8 ms of a 26.5 ms token is the CPU between the calls (next section, and #150).

What it means, in plain words. Since 2026-09-23 the tree has had a second door into the DSP: instead of the ARM calling the NPU once per MoE layer (22 calls per token), it can hand the DSP a description of the whole decode step and let the DSP run every op it has a kernel for before returning. PR #119 built the door with only the MoE kernel behind it; PRs #125 / #126 landed kernels for the norms, RoPE, the conv1d + gate and the decode attention; PR #133 (#130) put those five behind the door too and added a mask to open it for "MoE only". Nothing of that had run on a phone. This sitting asked three questions and answered all three. Does the door itself cost anything? No: C, the entry with MOE alone resident, reads +6.8 / +5.1 / +0.3 % against A — inside a warm phone's own spread — with byte-identical text. Plan 85's B, never measured until now, is free. Does putting the five small kinds behind the door pay? Not as wired, and by more than the plan expected: B reads −22 / −25 / −30 %. The op list still has an FC, an ADD or the router on the ARM between every resident stretch and the MoE op, so instead of fewer calls there are more — 95 per token — and the profile shows where the time goes: 20.9 ms of DSP time per token instead of 15.7, of which the attention kernel alone is 0.79 of a MoE op at pos 512, plus 73 extra round trips. The ride-along timed that kernel at ≈ 1.05 µs per KV position per layer — 3.2 ms per token at pos 512, 7.1 at pos 1024 — which is exactly why the loss widens with the generation length. Is the text right? No: with all six kinds on, the model leaves A's text at the first word and loops the same sentence; the user rejected it (#136). Rule 37 says why it is not the few-ulp differences the gtests found on subnormal rows: those cannot move a logit, so #136 is a logic or binding fault (the KV seed after the CPU prefill, the RoPE position offset at pos ≥ 512, the conv state seed, a graph_set_param binding the tiny host fixture never exercised).
